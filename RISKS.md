# Risk assessment

| Risk | Why it is hard | Mitigation | Severity |
|---|---|---|---|
| **Multiplayer synchronization** | Predicted movement, reconciliation and interpolation on mobile networks with jitter and loss. Desync shows up as rubber-banding. | Use Fusion's tick-based prediction and a proven KCC instead of a custom netcode. Keep simulation state small. Test early with simulated 100–200 ms latency and 2 % loss (Phase 3, not Phase 13). | High |
| **Server-authoritative shooting** | The shooter sees the past, so hits must be rewound per shot (lag compensation) without letting high-ping players shoot around corners. | Fusion lag-compensated hitboxes, a cap on the rewind window **[T 200 ms]**, server fire-rate and ammo checks, and hit markers shown only after server confirmation. Study BR200's patterns. | High |
| **Android performance** | URP plus 12–24 animated characters plus a 1.2 km map plus VFX on mid-range GPUs and thermals. | Low/Medium/High presets from day one, graybox first, LODs, occlusion, GPU instancing, pooled VFX, and profiling on a real device every phase from Phase 2. | High |
| **Offline bots at 23 on NIGHTMARE** | 24 agents doing perception raycasts, pathfinding and combat on a phone, while staying fair. | Staggered decision ticks, budgeted raycasts per frame, distance-based LOD for AI (cheaper but still simulated), shared navmesh, path caching. The capacity policy lowers the bot count on weaker devices. Thresholds get measured, not guessed. | High |
| **Anti-camping detection** | Telling real movement from wiggling, wall-walking and micro-movement without false positives (e.g. a player pinned in a firefight behind cover). | Server-sampled positions, net-displacement **and** path-length thresholds over a window, grace periods, tunable values, and structured logs to review false positives. Reconnecting never resets the timer. | Medium |
| **Safe-zone weapon lock** | Shots near the boundary while the player crosses it, under latency. The client must not be able to forge being inside. | Permission is evaluated on the server from the body position at the shot's tick, and only new shots are blocked. The client only greys out the button. Edge cases are unit tested. | Medium |
| **Matchmaking and hosting** | Dedicated-server orchestration, cold starts, region routing, cost. Unity Multiplay Hosting is discontinued. | Run locally first, then Docker, then Edgegap (which has Fusion support). Keep allocation behind an interface so the host can be swapped. Fill public matches from a queue with a timeout and offer offline mode. | Medium |
| **Fusion ↔ Unity 6.3 compatibility** | Fusion 2.0.x documentation lists Unity 6.0, and 6.3 support was not confirmed. | Verify first thing in Phase 3. Fallbacks: newer Fusion 2.0.x, or a documented Unity version change. Gameplay rules sit outside Fusion in `WarOfNyx.Core`. | Medium |
| **Play Store deployment** | Target API 36 requirement, AAB signing, data-safety form, content rating for a shooter, network permission disclosure. | Re-check Google's requirements before Phase 14. Use Play App Signing. Keep the upload keystore out of git and back it up. Collect minimal data. Write the privacy policy early. | Medium |
| **Scope** | The spec is a commercial-scale game. A solo developer can stall on art or backend. | Strict phase gates. Placeholder art until Phase 10. Backend is post-core. Every feature has acceptance tests. | High |
| **Licensing** | BR200 sample assets, anime look-alike content, third-party art. | Learn from patterns only, use original designs, and track licenses for any purchased or placeholder assets. | Medium |
